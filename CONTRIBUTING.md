# Contributing to Abyssal Whispers

Thank you for contributing. This repository combines open-source software with separately licensed creative content, so every contribution must keep that boundary clear.

## Before starting

1. Read `docs/adr/README.md` and the ADRs relevant to the area you will change.
2. Search existing issues and code for the established implementation pattern.
3. Keep the change focused. Do not reformat or rewrite unrelated files.
4. For a larger behavioral change, open an issue first so the design and content-license impact can be discussed.

## Contribution licenses

By intentionally submitting program code, tests, build scripts, configuration, or technical documentation for inclusion, you agree that your contribution may be distributed under the repository's MIT License. You must have the right to make that grant.

Creative contributions are different:

- Submit story text, dialogue, characters, art, audio, video, creative prompts or similar material only if you own it or have documented permission to contribute it.
- State in the pull request that owner-controlled creative material may be distributed under CC BY-NC-ND 4.0, and grant the project maintainers permission to edit it as needed for inclusion and maintenance.
- Do not copy third-party material merely because it is available online, generated by a service, or marked “free.” Provide the exact source and applicable terms.
- Do not mix a third-party asset into an existing owner-created asset unless the resulting work can legally be redistributed under the intended terms.

Submitting a pull request does not relicense material you do not own.

## Media and generated-content checklist

For every new image, audio, video, font or generated creative file, include the following in the pull request and update `THIRD_PARTY_NOTICES.md` when applicable:

- repository path and short description;
- creator/rights holder and source URL or source project;
- creation, retrieval or generation date;
- exact license or terms-of-service version and required attribution;
- for generated material: tool/service, model and checkpoint/version, prompt or reproducible source reference, and material edits;
- confirmation that repository redistribution and the intended project license are permitted.

If provenance cannot be documented, do not add the file.

## Development setup

```bash
npm ci
npm run dev
```

Node.js 20.19 or newer is required. Rust is needed only for the Tauri desktop shell.

## Project rules

- Application source in `src/` uses ESM JavaScript/JSX. Engine code remains JavaScript-only.
- Every consumed function must have an explicit import.
- Reducer randomness must use the reducer context RNG (`c.rng`); do not use bare `Math.random()` in reducers.
- Do not use `c` as a callback parameter because it shadows reducer context.
- Keep reducer context `c` separate from game-data context `ctx`.
- New `.js` files must be imported by their consumer so Vite includes them in the ESM graph.
- Preserve the program/content license boundary described by `LICENSE`, `LICENSE-ASSETS.md` and the nearest directory-level notice.

## Validation

Run checks proportional to the change. Before requesting review, the normal minimum is:

```bash
npm test
npm run build
node check_build.cjs --dist
node tests/test_full_flow.mjs
```

Also run the relevant gates:

```bash
npm run lint:schema
npm run lint:engine
npm run lint:undef
npm run lint:san
npm run lint:rng
npm run lint:audio
npm run lint:events
npm run analyze:events:ci
node scripts/validate-mods.mjs
```

After adding or changing events, run `npm run lint:narrative`. After changing NPC dialogue, run `npm run lint:npc`. Browser-facing changes should run `npm run test:e2e` against a production build where practical.

`npm run format:check` is currently advisory because the repository does not yet have a clean full-format baseline. Do not use broad auto-formatting to rewrite unrelated files.

## Pull requests

Describe:

- what changed and why;
- code/content license classification;
- third-party or generated-material provenance, if any;
- tests and commands run, including failures or skipped checks;
- screenshots for visible UI changes when useful.

Keep commits and pull requests free of API keys, private endpoints, personal data, generated build directories, and unrelated local files.
